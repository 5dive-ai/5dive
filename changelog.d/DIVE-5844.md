## Unreleased — fix(supervisor): a confirm that clears itself never pages (DIVE-5844)

At 2026-10-08 03:43Z a `[FLEET-HEALTH blocked-on-prompt]` page about `main` reached a phone for a
tool-permission confirm that claude's own harness timed out about a minute later — before anyone
read the page. DIVE-4536 let the class, the audited row and the page all fire on the first tick
that saw a confirm; only the Escape keystroke waited for the 10m decline window.

The page now waits for the window too. A confirm seen inside it (`promptMark=confirm-fresh`) is
**held**: the audited `supervisor_events` row is still written (DIVE-4052), under its own event
`alert-held` so the per-class dedup — which counts `event='alert'` — cannot let a held sighting
swallow the page a sticky confirm still owes; and the held page is counted, as
`promptPagesHeld` on the `(fleet)` heartbeat row and `N prompt page(s) held` on the tick summary
(the DIVE-4666 shape). A confirm still standing when the window ends pages once, as before: the
watchdog presses Escape and the page says whether it landed. A declined confirm used to end the
row quietly — it now falls through to that one page, because the first-sight page it relied on
no longer fires. Pickers (AskUserQuestion/ExitPlanMode) are unchanged.

Grading: `tests/supervisor_prompt_hold_unit.sh` (14 arms, end to end through
`cmd_supervisor_tick` on a scratch store), including a page-on-first-sight mutant run through the
transient-confirm arm; 10 of its arms are red on the pre-fix tree.

`5dive-cli` does not auto-deploy: the held pages start when a release cut lands on the host.
