## Unreleased — fix(task): a row delivered with a commit URL can leave the merging stage (DIVE-5758)

On a repo where agents push straight to main, a row is delivered with
`task deliver --pr=https://github.com/<owner>/<repo>/commit/<sha>`, because there is no
pull request to bind. After the verifier PASSed, `task merge-landed` asked GitHub about a
pull request, got no `mergedAt`, and refused, even though the sha was on main.
`task merge-declined` recorded a false "no landing" and handed the row back to its maker.
The re-delivery PASSed again, and the cycle repeated. `task unbind-pr` rejected the commit
URL outright.

- The landing read (`_merge_landed_probe`, shared by `merge-landed`, the forge poller,
  `task merge` and the companion check) now answers for a commit URL. It compares the
  repository's default branch with the sha on GitHub: `behind` or `identical` means the
  commit landed, and the landing is recorded with the full sha. `ahead` or `diverged`
  means it did not. Anything else writes nothing. It uses the same credential-free rails,
  then the seat's owner-scoped read token, which is now also picked from a
  `gh api repos/<owner>/…` path.
- `merge-landed` refuses a commit that is not on the default branch, and says so
  ("not on main (compare: diverged)"). A forge that could not be asked gets a separate
  refusal.
- A commit URL is a bound ref: `unbind-pr` drops one bound beside the primary, a second
  `--pr` may be one, and a commit primary is refused as the primary, with the refusal
  naming `merge-landed`.

`tests/task_commit_url_delivery_unit.sh` covers all three, plus two mutants.
