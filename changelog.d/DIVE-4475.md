## Unreleased — fix(plugin): `plugin setup` runs the publisher's command as the CALLING SEAT, so the browser plugin's host half can be installed at all (DIVE-4475)

`5dive plugin setup browser` could not succeed on any box. Measured on this host, 5dive 0.38.0:

```
sudo 5dive plugin setup browser --yes   -> 1  (setup exited 64)
    5dive browser: refusing to make root a browser seat — run this via sudo from the
    seat that will own the profiles, so SUDO_USER names it.
```

The verb ran `bash -c "$setup_cmd"` while already root, and `setup.command` is — by the verb's own
comment — "the same string a human was told to paste". Both shipped commands begin with `sudo`
(`sudo 5dive browser setup`, `sudo 5dive-setup-voice`): they self-elevate, so they are written for a
NON-root caller. `sudo` sets `SUDO_USER` to *its own* invoking user, so from a root caller the inner
sudo rewrote the seat to `root` one process later:

```
sudo bash -c 'echo $SUDO_USER; sudo bash -c "echo \$SUDO_USER"'
  agent-dev     <- our process
  root          <- the publisher's
```

Exporting the seat cannot fix this: with `Defaults env_reset` no variable of any name survives the
inner sudo, and `SUDO_USER` is overwritten regardless. Only the real uid crosses an arbitrary inner
`sudo`. So when we are root and the caller is not, the command now runs under
`runuser -u <caller> --`, and the caller's own sudo re-derives the seat honestly. A root caller and
an unprivileged caller take the previous path unchanged.

`runuser`, not `sudo -u`: `sudo -u` asks the sudoers policy for permission to become the caller and
this fleet narrows runas on purpose (DIVE-3263), so a policy-gated drop is the one that fails first
on the boxes most likely to have been hardened. `runuser` is root-only by construction and consults
no policy. `sudo -u` remains the fallback where util-linux is absent.

The consent screen now names the seat it will run as instead of claiming "as root", and the receipt's
`by` is that same seat.
