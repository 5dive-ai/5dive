## Unreleased — fix(trace): `trace` counted human touchpoints off the live row only, so a human-cleared task verdicted `zero-human` (DIVE-4552)

`5dive trace` read the human-gate count and the timeline's `gate` event off `need_answered_at` /
`need_answered_by` on the **live** `tasks` row. A tasks row carries at most **one** gate epoch:
`_gate_archive_and_clear_sql` copies the answered epoch into `gate_history` and nulls those columns
on every re-file, withdraw, park and loop-ceiling park. So the moment a second gate was filed on a
row, the human who cleared the first one vanished from the count — and once that row reached `done`
the verdict read `zero-human — goal to done with 0 human touchpoints`, which is the product's
headline claim stated falsely.

The contradiction was visible **inside one invocation**, which is how a customer (agent luca,
teal-fox box-1, 0.40.0) found it: the append-only audit reference printed
`gate.answered  human:…  decision gate cleared by human:… (human touchpoint)` and, three lines
later, `verdict: in progress — 0 human touchpoint(s) so far`. The audit log was right; the derived
count was wrong.

Both readers now come from one SQL fragment (`_trace_gate_epochs_sql`) over the **durable** record:
answered epochs in `gate_history`, UNION the live row's epoch when it has not been archived yet.
There is no double count, structurally — the archive INSERT and the UPDATE that nulls the live
answer columns are one pair inside one transaction, so an epoch is in one source XOR the other.
Sharing the source is the point rather than tidiness: the defect was two readers of the same fact
disagreeing, and they can no longer diverge.

Two further corrections fell out of it:

- **A pending gate no longer erases the touchpoints already cleared.** The in-progress verdict said
  only `blocked on a pending <type> gate`; it now names both, which is exactly the state luca's row
  was in.
- **A zero from a partial archive is qualified, not asserted.** `gate_history` reaches back only to
  its own coverage boundary (`gate_history_coverage`, DIVE-2133); epochs displaced before it were
  destroyed outright. On a task older than that boundary the verdict now says the count is
  *recorded*, and `--json` carries a `human_touchpoints_coverage` envelope so a JSON consumer cannot
  publish the bare number the text refused to assert. A non-zero count is not caveated — the caveat
  is about the zero.

Measured on this control plane's store (read-only snapshot, 2026-09-15): **52 of 2605 `done` rows**
were verdicted `zero-human` with a human-cleared gate in their archive, and 27 more carried a count
that was merely too low. Spot check: DIVE-4355, DIVE-2224 and DIVE-2034 each read
`zero-human — goal to done with 0 human touchpoints` before and
`human-in-the-loop — N human gate(s) required` after.

Graded by `tests/trace_human_touchpoint_history_unit.sh` (24 assertions; 10 of them red against the
pre-fix source).
