## Unreleased — feat(team): a hired team asks first, and nothing starts until the owner says yes (DIVE-5729)

`team import` used to file every seeded `goals:` entry live and install every `loops:` entry
live on its cron, so a hired team started spending the owner's AI on work nobody had
confirmed. On a team's FIRST start, all of that work is now born blocked behind one kickoff
row assigned to the lead. The kickoff tells the lead to send its owner one short plan (at most
60 words, where they normally talk) and to wait. The lead's standing instructions say it too,
so a fresh session still knows what the owner's "yes" is answering.

- `5dive team plan [<lead>]` lists what is waiting: each goal and recurring job, who owns it,
  and how often a job runs.
- `5dive team start [<lead>] [--skip=<DIVE-N>,...]` releases it. A skipped goal is cancelled.
  A skipped job never switches on, and a later re-import does not bring it back. Every `--skip`
  is checked first, so a typo starts nothing.
- `5dive team decline [<lead>]` starts none of it.
- `team import --start-now` (and `up --start-now`) keep the old behaviour.

The hold covers the first start only. A re-import of a team that is already running asks
nothing, and once released, loops run on their schedule with no further asks.

The hold is a dependency edge, so the dispatcher and the recurring materializer skip held rows
with no scheduler change. `task add` gains `--held-by=<row>` and `--park=<why>
--park-wake=<+Nh|+Nd>`. Both write the hold in the same transaction as the row, so no tick
can start the row in between. `loop install` passes `--held-by` through.

Also fixed: a role created before its manager lost its goals, because `--from=<manager>` named
an agent that was not on the box yet. Goals are now filed after the whole roster is up.

`tests/team_plan_first_unit.sh` runs the real `cmd_compose_up` against a real task store, with
the real CLI and the real recurring materializer on a cron that is due every minute: 20 arms,
and 7 mutants that each turn it red.
