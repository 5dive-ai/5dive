## Unreleased — feat(local): office panel invites a person by name and sets up the office AI on first run (DIVE-7599)

The office panel (`/panel`, owner devices only) could remove a device but not add one, and a
box with no AI account could only be set up from a terminal. An office owner has no terminal,
so both needed IT. Both are now in the panel.

**Invite a person.** Settings → Connected devices → "Invite a person": type their name, pick
Chat or Manage, and the panel shows the one-time code, the office address and the certificate
fingerprint to hand over. The device that uses the code shows under that name and role. It is
the same code `sudo 5dive local pair` makes (one use, 15 minutes, only its hash is stored),
issued through the panel's one root entry as `local pair --name=<name> [--owner]`. Each invite
writes one audit line with the device, name and role. The code is never in it. A chat-only
device gets 403 on the new route, like every `/api/panel/*` route.

**First-run AI setup.** On a box with no AI account, the panel opens on a setup sheet. It looks
for AI model servers with the new `5dive account scan`: one `GET /v1/models` to this box and to
the /24 around each private address the box has, on Ollama's, LM Studio's, vLLM's and
llama.cpp's ports. It dials private addresses only, so a local-only box stays local-only. The
owner picks a model or types an address. Then one tap tests it with `account test` (Claude
first, hermes for a server that speaks only OpenAI's format), saves it as the `office-ai`
account and creates the first agent in the office chat. Nothing is saved until the test passes.
Once the box has an AI account, the panel will not move it (`account add --replace` from a
terminal does).

`tests/local_panel_unit.sh` (167 checks) runs the real server on bun with the real panel-exec,
the real `local pair` and the real scan and test. A stub model server sits on 127.0.0.2. On the
code before this change, 24 of the new checks fail.
