## Unreleased — fix(task): a command grade stamps the sha it graded so the merge gate can clear (#1001)

`_gate_graded_sha` is a fence by design: it matches a labelled `graded-sha:` declaration and
nothing else, because a result routinely names shas it did not grade. A row graded by a COMMAND
(`--review=check`) recorded `✅ verify PASS (exit 0): <cmd>` and no such line, so the fence read
empty — and everything downstream reads that fence.

`_merge_disp_decide` therefore answered `hold:merger:no-graded-sha-stated` (DIVE-2656's rule read
forwards: a grade is bound to a sha, not to a pull request), and `task done` refuses a close whose
result states no graded sha, with the audited `--no-graded-sha` as the only escape. So a row that
had just passed its own acceptance command could be closed by nobody. Measured on a delivery where
verify passed at 04:40Z and the row sat held until a person appended the sha by hand after the
merge.

The sha was never unknown at any step — the command ran against the delivered head and the
delivery record names it; it simply was not written down. The PASS branch of `cmd_task_verify` now
states it on a bound row: the pull request head at grade time read with `gh`, falling back to the
maker's `DELIVERED-SHA`, naming which of the two it used. With neither readable it writes a line
that says so and carries NO hex, so the fence still reads empty and the gate still holds — the
hold is made legible, never lifted. A `graded-sha` the verifier stated themselves is left alone.

`tests/verify_command_grade_stamps_sha_unit.sh` stubs the gh seam and grades WHERE the sha came
from, not merely that one arrived: the gh read, the fallback, the neither-readable hold, a stated
claim being preserved, an unbound row taking no stamp and still auto-closing, and a FAIL stamping
nothing. Mutant arms disable the stamp and require the gate back at `no-graded-sha-stated`.
