## Unreleased — fix(agent): dispatched work reaches a codex seat that has a channel (DIVE-4036)

`5dive-agent-start` gives a **codex** seat with `telegram` or `dashboard` in its channels a
different pane process — the app-server dispatcher, not the codex CLI (PR #770, DIVE-3961). Every
delivery site kept typing into that pane with `tmux send-keys`, so the keystrokes landed in the
dispatcher's stdin and were discarded. **The model never saw the message.** `agent list` said
active, `agent info` said transacting, the board said `in_progress`, and the seat had been deaf for
~2.2 days before a human noticed a task had not moved. `dashboard` is the common channel on
customer boxes, so this was never limited to Telegram.

Work now goes into the dispatcher's file inbox (`~/.codex/channels/dispatcher/inbox`) with
`route.source: "agent"`, which the dispatcher drains and whose replies it deliberately does not
publish to a customer channel. The dispatcher unlinks the file on submit, so **the message
disappearing is the delivery receipt** — a harder proof than the pane path's placeholder-cleared
heuristic, and an unconsumed message is now reported as *not delivered* instead of green.

The delivery mode is not re-derived. `5dive-agent-start` has already evaluated the predicate that
chose the pane process, so it writes the answer to `~agent-<name>/.5dive/delivery.env` and the
delivery path reads it: one evaluation, not two that must agree. A box whose boot script predates
this falls back to evaluating the same predicate against the same `agents.d/<name>.env`, and
`tests/codex_dispatch_delivery_unit.sh` asserts the two predicate bodies are byte-identical.

Known residual, named rather than papered over: a *fresh* wake on a dispatcher seat is not fresh.
`/clear` has no meaning to the dispatcher (it owns one app-server thread and every inbox message is
a user turn), so control lines are skipped and logged rather than submitted as stray user text. A
thread-reset verb on the inbox schema is the follow-up.
