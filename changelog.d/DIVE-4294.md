## Unreleased — feat(install): record which tag resolve_cli_target picked, and from which rung (DIVE-4294)

- `install.sh` now writes a resolution RECEIPT to `/var/lib/5dive/cli-target.json` on the
  success path — the tag it resolved, the rung it came from (`override`, `canary`, `route`,
  `last-known`), the detail that rung was read from, and a UTC stamp. The answer previously
  existed only in the resolver's locals: stdout is the return value (every caller does
  `GH_PINNED_TAG="$(resolve_cli_target)"`) and stderr is swallowed by the soft-update's
  exec-into-log, so "Updates started" followed by the same version could not say why.
- `5dive update --check --json` reads that receipt back as `resolvedTarget`, `resolvedRung`,
  `resolvedRungDetail` and `resolvedAt` — all nullable, absent on a box that has not yet
  re-run install.sh. The ladder is NOT re-implemented CLI-side; `resolve_cli_target` stays the
  single authority and the CLI only reads what it wrote.
- `rung` is its own key: `source` in that JSON already means "the ref the answer came from",
  and `latest` means "newest published", not what THIS box installs. A pinned box and a canary
  box on the same tag report an identical `latest` and differ only in the rung — the case that
  produced the original "why it skipped update?".
- Writing is best-effort and silent on both streams: an unwritable state dir, a failed resolve
  and a refused downgrade all write no receipt and cannot fail an install.
